# Ferrite Architecture

Ferrite splits the framework into a Rust engine and a JavaScript/TypeScript facade.

## Rust Engine

- `ferrite-builder`: production build manifests, static route prerendering, client bundle injection, and explicit server-action reference manifest collection.
- `ferrite-client-bundler`: Rust wrapper around the JS browser bundler, client-reference scanner, protocol validation, static asset/WASM emission, and client-reference chunk emitter used by dev/build orchestration.
- `ferrite-core`: virtual tree types, validation, and HTML rendering.
- `ferrite-dev-server`: TSX-backed development server, route manifest rebuilds, static client asset serving, server-payload JSON/frame route responses, form-based server-action POST handling, explicit action references in the build manifest endpoint, and polling reload client.
- `ferrite-protocol`: render-packet/render-stream/client-reference/server-payload/server-payload-frame/server-action markers, versioning, packet shapes, and validation intended to become the native/WASM protocol boundary.
- `ferrite-protocol-wasm`: WASM build of Rust-owned server-payload packet and stream-frame validation for browser-capable JavaScript consumers.
- `ferrite-router`: app-directory route discovery, layout/loading/error convention discovery, and route type generation.
- `ferrite-ssr`: legacy serialized VNode decoding, versioned compact render-packet, render-stream, and server-payload decoding, plus server-side HTML rendering.
- `ferrite-node`: a minimal Node-API addon exposing the Rust SSR renderer to JavaScript consumers.
- `ferrite-cli`: human-first CLI for route inspection and project checks.

The Rust side should own work that benefits from predictable performance and strong validation: compiler passes, route manifests, SSR orchestration, generated types, dev-server routing, and build output.

## TypeScript Facade

- `@ferrite/protocol`: browser-safe TypeScript protocol package generated by Rust protocol codegen, exporting markers, versions, packet types, builders, and validators without depending on the DOM runtime or native Node bindings.
- `@ferrite/protocol-wasm`: TypeScript wrapper for the Rust `ferrite-protocol-wasm` artifact, exposing server-payload packet and stream-frame JSON validation through browser-capable WASM. Generated browser bundles can import its `.wasm` artifact and emit it under Ferrite's static asset path.
- `@ferrite/runtime`: JSX runtime, component types, `Suspense`, public hooks API, route-related types, and compatibility re-exports for the generated protocol APIs.
- `@ferrite/runtime/dom`: browser DOM mount/hydrate helpers, client-reference hydration, server-payload fetch/application helpers, incremental stream-frame application, same-origin payload navigation helpers with opt-in stream mode, managed head reconciliation, popstate restoration, payload prefetching, and idempotent server-action form enhancement/bootstrap.
- `@ferrite/runtime/server`: server helpers for rendering page modules, route loading/error conventions, and layout chains to legacy serialized VNodes, versioned render packets, versioned render-stream packets, or versioned server-payload packets, plus page/layout metadata collection, explicit `createServerAction()` form action references, and rendered-route server-action manifest collection.
- `@ferrite/node`: JavaScript package wrapper for the native Node addon, currently exposing `renderJsonToHtml(input: string): string`, resolving native bindings from an explicit override, local source build, or checksum-verified supported optional platform prebuild package, and validating generated prebuild package artifacts through a dry-run release workflow.
- `scripts/verify-npm-packages.mjs`: local release verifier for JS-facing npm package tarballs. It builds public packages, validates locally knowable package metadata, writes release-shaped manifests into temporary staging copies, runs real `npm pack --json` into temporary tarballs, validates packed file lists, inspects each packed `package/package.json`, rejects `private` and `workspace:*` in packed manifests, installs all generated tarballs together in a clean offline temp project with optional native dependencies omitted, smoke-imports the protocol/runtime/WASM-safe packages, checks the `@ferrite/node` tarball is installed without importing its unpublished optional native binding path, writes release and packed manifests to `dist/npm-packages/npm-package-report.json`, and leaves repository/homepage/bugs proof gated on a configured GitHub remote. Source package manifests stay private and workspace-shaped for development.
- `packages/runtime/bin/render-page.mjs`: TSX page executor used by Rust dev/build orchestration; render/document modes emit versioned compact render packets, stream modes emit fallback shells plus resolved chunks, server-payload modes emit compact shells/chunks plus client-reference payloads, and server-action-manifest mode emits explicit form action references discovered during route render.
- `packages/runtime/bin/build-client.mjs`: browser bundle executor used by Rust dev/build orchestration; it skips route bundle emission unless the page or one of its layouts starts with `"use client"`, records, emits, and injects browser chunks for server-route imports of separate `"use client"` modules, and can emit a standalone action-form bootstrap chunk for server-only action routes that have no client-reference script.
- `docs/deployment.md`: operator-facing deployment guide for the current production adapter, including proxy/TLS assumptions, build/start commands, smoke tests, observability, rollback, and known security gaps.

The TypeScript facade exists for developer ergonomics. It should remain thin, typed, and compatible with normal TSX tooling. Browser DOM work and the current esbuild bridge live here because DOM and JS module graphs are JavaScript-native; Rust owns orchestration, routing, validation, SSR, static output, native SSR binding, protocol codegen, and CLI behavior.

## TypeScript Strategy

Ferrite should parse and transform TS/TSX in Rust, but semantic TypeScript compatibility should initially be delegated to the official TypeScript compiler. Reimplementing TypeScript's checker is out of scope until the rest of the framework is proven.

The CLI therefore treats TypeScript as an automatic project check:

1. Discover app routes.
2. Generate `.ferrite/types/routes.d.ts`.
3. Run local `tsc --noEmit --project tsconfig.json`.

## Route Conventions

Ferrite scans for the nearest `loading.{tsx,ts,jsx,js}` and `error.{tsx,ts,jsx,js}` from the app root down to each page directory. Rust carries those paths in the route manifest and passes them to the TSX page executor during dev/build rendering.

- `loading.tsx` wraps streamed page output as a server `Suspense` fallback. Non-stream dev/build output still waits for the final page tree.
- `error.tsx` wraps the page tree with a server error boundary and renders `{ error }` when the page subtree fails. Layout failures outside that page boundary still surface as render errors.

The dev server renders matched HTML routes through the stream packet path and keeps both representations: a buffered HTML body for tests and `--once`, plus shell/chunk parts for real HTTP sockets. The socket writer emits `Transfer-Encoding: chunked` only when stream chunks exist; routes without deferred chunks keep `Content-Length`. Matched app routes can also negotiate the raw validated server-payload protocol JSON with `?__ferrite_payload=server` or line-delimited shell/chunk frames with `?__ferrite_payload=stream`; unsupported reserved payload values return `400 Bad Request`.

The production HTTP adapter uses the same stream response model without dev reload state. `ferrite serve` scans routes once, writes route types, renders matched requests on demand, serves generated client assets from `/_ferrite/static`, exposes validated server-payload JSON for `?__ferrite_payload=server`, exposes line-delimited server-payload frames for `?__ferrite_payload=stream`, accepts same-origin form `POST /_ferrite/action` server-action submissions, rejects action POSTs when a browser-supplied `Origin` or `Referer` host does not match the request `Host`, can validate action `Origin`/`Referer` against an explicit trusted proxy public origin through `X-Forwarded-Proto` and `X-Forwarded-Host`, can require a hidden server-action CSRF token loaded from `--server-action-csrf-token-env`, gzip-compresses eligible HTML and payload responses when `Accept-Encoding` allows it, and keeps `data-ferrite-build-id`, `/__ferrite/client.js`, and dev manifests out of production HTML. Production HTML, payloads, action responses, and errors use `Cache-Control: no-store`; content-fingerprinted generated client assets use immutable long-lived caching; unknown or non-fingerprinted static assets stay on conservative revalidation. Production route HTML emits `rel="modulepreload"` hints for generated scripts, real HTTP responses mirror those script hints in `Link` headers, and route responses expose `X-Ferrite-Route-Pattern` for deployment/logging metadata. `ferrite serve` runs production sockets through a reusable worker pool sized by the configurable in-flight request limit, with CLI flags for request-read-timeout, maximum request bytes, in-flight request count, per-render subprocess timeout, opt-in server-action CSRF token enforcement, trusted-proxy public-origin validation, and stderr access logs in plain or JSON format; renderer timeouts return `504 Gateway Timeout`, and production request observers can record method, path, status, route pattern, and elapsed duration without logging headers or bodies. Embedders can run a shutdown-aware production listener that stops accepting new sockets and drains accepted work before returning. `--once` returns the buffered body for deterministic checks; real sockets use chunked transfer when stream chunks exist.

Server actions are currently form-based and explicit. A server-rendered `<form action={createServerAction({ id, run })}>` becomes a same-origin `POST /_ferrite/action` with hidden `__ferrite_action` and `__ferrite_route` fields, plus hidden `__ferrite_csrf` when the Rust renderer is configured with a server-action CSRF token. Rust requires a valid `Host` header for action POSTs, rejects a present `Origin` or `Referer` host that differs from the request `Host` by default, switches to a configured trusted proxy public origin when `--trusted-proxy-public-origin` or `ProductionTrustedProxyConfig` is set, rejects missing or mismatched `X-Forwarded-Proto`/`X-Forwarded-Host` in that trusted-proxy mode, rejects missing or mismatched `__ferrite_csrf` values when a token is configured, then parses urlencoded forms and small text multipart forms, rejects file parts, validates the server-action request shape through `ferrite-protocol`, matches the submitted route path against the app router, invokes the page renderer in `--server-action` mode, and returns validated `server-action-response` JSON. `@ferrite/runtime/dom` exposes `enhanceServerActionForms()` for explicit integration and `bootstrapServerActionForms()` for generated browser entrypoints; route client bundles, client-reference chunks, and standalone server-only action bootstrap chunks call the bootstrap helper on `document` and the helper deduplicates per event root. Build output and the dev build manifest endpoint now include explicit `server_action_manifests` entries collected from rendered `createServerAction()` form references, and the client bundle manifest can include an `actionBootstrap` script while keeping route-level `script: null`. A Chromium-backed test builds a temporary Ferrite app and proves enhanced form submissions stay on-page and send `FormData` for route, island, and server-only action assets. This does not yet include automatic `"use server"` export discovery, deployment-stable inferred action ids, persistent deployment registries, session-bound token rotation, replay protection, cross-origin action calls, upload streaming, client event actions, or forwarded client-IP trust policy.

## Client Hydration Boundaries

Routes are server-first. The browser bundler inspects the matched page and layout chain for a leading `"use client"` directive before doing any esbuild work. If no directive is present, the route returns a server-only bundle record with `script: null`, empty asset lists, and no generated route files. Client and client-reference bundles use esbuild file loaders for imported binary/static assets, including `.wasm`, and pass Ferrite's configured static public path into esbuild so generated browser code references emitted assets through `/_ferrite/static/...` rather than temp-directory-relative URLs. Production builds remove the static client output directory before rebuilding so a route that becomes server-only cannot keep stale scripts from an earlier build.

Server-only routes also scan their relative import graph. When that graph reaches a module with a leading `"use client"` directive, the scanner records the boundary in `clientReferences` with a stable `module`, `exportName`, and `id` of `module#exportName`. The scanner stops at that boundary instead of traversing into the client module's dependencies, then emits a browser chunk for that reference. Each reference records its own `script`, `styles`, `outputs`, `sourcemaps`, and `assets`; the parent route bundle aggregates those outputs while keeping route-level `script: null`.

The runtime island contract is explicit, but app code no longer writes the marker by hand for imported client components. During server page bundling, nested modules with a leading `"use client"` directive are replaced with server-side client-reference proxies. A proxy renders a `<span>` island container with `data-ferrite-client-reference="module#exportName"`, legacy JSON `data-ferrite-client-props`, a versioned `data-ferrite-client-payload` containing `{ ferrite, version, id, module, exportName, props }`, and fallback HTML from the original client component. The emitted client-reference chunk registers the real browser component and calls `hydrateClientReference()`, which validates the payload, hydrates matching containers, and marks them with `data-ferrite-client-hydrated="true"`. Rust validates the JS-produced manifest entries before build/dev adapters consume them.

The `server-payload` protocol packet is the first RSC-style transport layer. It carries a compact shell, shell-level `clientReferences`, deferred stream chunks, and per-chunk `clientReferences`. The Rust protocol crate owns validation, the generated `@ferrite/protocol` package exposes `validateServerPayloadPacket()`, `@ferrite/protocol-wasm` exposes Rust-backed `validateServerPayload()` for full packets, `@ferrite/runtime/server` emits payloads from the same rendered tree used for HTML, `ferrite-page-renderer` can request page/document payloads through `--server-payload` and `--document-server-payload`, and dev/production adapters can return those validated packets directly over HTTP. The protocol crate also owns a line-delimited `server-payload-frame` contract for incremental payload application: one validated shell frame followed by zero or more validated chunk frames. Dev and production adapters expose that framed contract over HTTP with `?__ferrite_payload=stream`; `@ferrite/protocol-wasm` also exposes Rust-backed `validateServerPayloadStreamFrameJson()` and typed `validateServerPayloadStreamFrame()` helpers for those frames.

The DOM runtime can fetch a server-payload response for a route, validate it, merge returned chunk roots into matching `data-ferrite-suspense-boundary` shell markers, convert compact nodes back into Ferrite children, and apply the result through the existing mounted-root update path. It can also consume a readable stream of line-delimited server-payload frames, commit a validated shell before deferred chunks arrive, then apply later validated chunk frames through the same compact-node/chunk path. The navigator helper wraps a mounted root, exposes an explicit same-origin prefetch API, optionally prefetches safe links on pointer/focus intent, consumes prefetched packets once during navigation, intercepts safe same-origin link clicks, applies payload responses, can opt navigation and popstate restoration into `?__ferrite_payload=stream` with JSON fallback before shell commit, updates history with `pushState`/`replaceState`, stores payload URLs in framework-marked history state, restores marked back/forward entries through the same payload path, extracts the route root from document-shaped payloads when possible, reconciles framework-managed title/meta/link/script/style head nodes while preserving unrelated head nodes, and falls back to normal navigation after failed intercepted or restored payload requests. A Chromium-backed integration test now proves same-origin prefetch consumption, URL/title updates, stream shell fallback rendering, later chunk application, stream-mode back/forward popstate restoration, malformed programmatic payload rejection without DOM/history mutation, and malformed clicked-payload fallback to normal document navigation against real browser fetch, stream bodies, and history APIs.

This is a working imported-client island boundary with a first server payload stream and first form-based server-action transport. It proves the Rust orchestration can distinguish server modules, whole-route client modules, imported client references, and explicit route-scoped action references through static output, manifests, emitted browser artifacts, automatic server markers, runtime hydration, HTTP payload responses, browser payload application/navigation helpers, incremental browser stream-frame consumption, HTTP frame-stream negotiation, navigator stream-mode selection, form POST action invocation, explicit action manifest emission, idempotent generated browser action-form bootstrap for route, client-reference, and server-only action assets, Chromium-backed action form enhancement proof, Chromium-backed payload prefetch/navigation, stream-frame, popstate, malformed-payload rejection, and malformed clicked-payload fallback proof, gzip response compression, managed head reconciliation, popstate restoration, payload prefetching, immutable production asset fingerprints, preload hints, bounded production request handling, production render timeouts, request observer hooks, trusted-proxy public-origin checks for action POSTs, graceful production shutdown, reusable production workers, an operator-facing deployment guide, validated payload/action packets, a generated browser-safe protocol package, a Rust-backed WASM protocol validation package for full server-payload packets and stream frames, generated browser-bundle emission for protocol WASM assets, native Node binding resolution that can use source builds or checksum-verified optional platform prebuild packages, a dry-run native prebuild workflow that builds and verifies package artifacts without publishing, and a local npm package verifier that inspects and clean-installs JS-facing staged tarballs without registry credentials. It is not yet Flight-compatible React Server Components, and production distribution still lacks npm-published WASM/native packages, remote CI proof for this local checkout, concrete process manager/container/platform deployment templates, code-signing/notarization, and automated npm release publishing.
