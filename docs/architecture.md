# Ferrite Architecture

Ferrite splits the framework into a Rust engine and a JavaScript/TypeScript facade.

## Rust Engine

- `ferrite-builder`: production build manifests, static route prerendering, and client bundle injection.
- `ferrite-client-bundler`: Rust wrapper around the JS browser bundler, client-reference scanner, protocol validation, and client-reference chunk emitter used by dev/build orchestration.
- `ferrite-core`: virtual tree types, validation, and HTML rendering.
- `ferrite-dev-server`: TSX-backed development server, route manifest rebuilds, static client asset serving, and polling reload client.
- `ferrite-protocol`: render-packet/render-stream/client-reference markers, versioning, packet shapes, and validation intended to become the native/WASM protocol boundary.
- `ferrite-router`: app-directory route discovery, layout/loading/error convention discovery, and route type generation.
- `ferrite-ssr`: legacy serialized VNode decoding, versioned compact render-packet and render-stream decoding, and server-side HTML rendering.
- `ferrite-node`: a minimal Node-API addon exposing the Rust SSR renderer to JavaScript consumers.
- `ferrite-cli`: human-first CLI for route inspection and project checks.

The Rust side should own work that benefits from predictable performance and strong validation: compiler passes, route manifests, SSR orchestration, generated types, dev-server routing, and build output.

## TypeScript Facade

- `@ferrite/runtime`: JSX runtime, component types, `Suspense`, public hooks API, route-related types, and a TypeScript-side protocol mirror generated by Rust protocol codegen.
- `@ferrite/runtime/server`: server helpers for rendering page modules, route loading/error conventions, and layout chains to legacy serialized VNodes, versioned render packets, or versioned render-stream packets, plus page/layout metadata collection.
- `@ferrite/node`: JavaScript package wrapper for the native Node addon, currently exposing `renderJsonToHtml(input: string): string`.
- `packages/runtime/bin/render-page.mjs`: TSX page executor used by Rust dev/build orchestration; render/document modes emit versioned compact render packets, and stream modes emit fallback shells plus resolved chunks.
- `packages/runtime/bin/build-client.mjs`: browser bundle executor used by Rust dev/build orchestration; it skips route bundle emission unless the page or one of its layouts starts with `"use client"`, and records, emits, and injects browser chunks for server-route imports of separate `"use client"` modules.

The TypeScript facade exists for developer ergonomics. It should remain thin, typed, and compatible with normal TSX tooling. Browser DOM work and the current esbuild bridge live here because DOM and JS module graphs are JavaScript-native; Rust owns orchestration, routing, validation, SSR, static output, native SSR binding, and CLI behavior.

## TypeScript Strategy

Ferrite should parse and transform TS/TSX in Rust, but semantic TypeScript compatibility should initially be delegated to the official TypeScript compiler. Reimplementing TypeScript's checker is out of scope until the rest of the framework is proven.

The CLI therefore treats TypeScript as an automatic project check:

1. Discover app routes.
2. Generate `.ferrite/types/routes.d.ts`.
3. Run local `tsc --noEmit --project tsconfig.json`.

## Route Conventions

Ferrite scans for the nearest `loading.{tsx,ts,jsx,js}` and `error.{tsx,ts,jsx,js}` from the app root down to each page directory. Rust carries those paths in the route manifest and passes them to the TSX page executor during dev/build rendering.

- `loading.tsx` wraps streamed page output as a server `Suspense` fallback. Non-stream dev/build output still waits for the final page tree.
- `error.tsx` wraps the page tree with a server error boundary and renders `{ error }` when the page subtree fails. Layout failures outside that page boundary still surface as render errors.

The dev server renders matched HTML routes through the stream packet path and keeps both representations: a buffered HTML body for tests and `--once`, plus shell/chunk parts for real HTTP sockets. The socket writer emits `Transfer-Encoding: chunked` only when stream chunks exist; routes without deferred chunks keep `Content-Length`.

The production HTTP adapter uses the same stream response model without dev reload state. `ferrite serve` scans routes once, writes route types, renders matched requests on demand, serves generated client assets from `/_ferrite/static`, and keeps `data-ferrite-build-id`, `/__ferrite/client.js`, and dev manifests out of production HTML. Production HTML and errors use `Cache-Control: no-store`, generated client assets use conservative revalidation caching, and route responses expose `X-Ferrite-Route-Pattern` for deployment/logging metadata. `--once` returns the buffered body for deterministic checks; real sockets use chunked transfer when stream chunks exist.

## Client Hydration Boundaries

Routes are server-first. The browser bundler inspects the matched page and layout chain for a leading `"use client"` directive before doing any esbuild work. If no directive is present, the route returns a server-only bundle record with `script: null`, empty asset lists, and no generated route files. Production builds remove the static client output directory before rebuilding so a route that becomes server-only cannot keep stale scripts from an earlier build.

Server-only routes also scan their relative import graph. When that graph reaches a module with a leading `"use client"` directive, the scanner records the boundary in `clientReferences` with a stable `module`, `exportName`, and `id` of `module#exportName`. The scanner stops at that boundary instead of traversing into the client module's dependencies, then emits a browser chunk for that reference. Each reference records its own `script`, `styles`, `outputs`, `sourcemaps`, and `assets`; the parent route bundle aggregates those outputs while keeping route-level `script: null`.

The runtime island contract is explicit, but app code no longer writes the marker by hand for imported client components. During server page bundling, nested modules with a leading `"use client"` directive are replaced with server-side client-reference proxies. A proxy renders a `<span>` island container with `data-ferrite-client-reference="module#exportName"`, legacy JSON `data-ferrite-client-props`, a versioned `data-ferrite-client-payload` containing `{ ferrite, version, id, module, exportName, props }`, and fallback HTML from the original client component. The emitted client-reference chunk registers the real browser component and calls `hydrateClientReference()`, which validates the payload, hydrates matching containers, and marks them with `data-ferrite-client-hydrated="true"`. Rust validates the JS-produced manifest entries before build/dev adapters consume them.

This is a working imported-client island boundary. It proves the Rust orchestration can distinguish server modules, whole-route client modules, and imported client references through static output, manifests, emitted browser artifacts, automatic server markers, and runtime hydration. It is not yet a React Server Components transport.
