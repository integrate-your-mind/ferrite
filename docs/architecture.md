# Ferrite Architecture

Ferrite splits the framework into a Rust engine and a JavaScript/TypeScript facade.

## Rust Engine

- `ferrite-builder`: versioned production artifact manifests, strict artifact loading/integrity validation, staged output installation with rollback, self-contained server modules, static route prerendering, route-level client bundles, and build-observed server-action metadata.
- `ferrite-client-bundler`: Rust wrapper around the JS browser bundler, client-reference scanner, protocol validation, static asset/WASM emission, and client-reference chunk emitter used by dev/build orchestration.
- `ferrite-core`: virtual tree types, validation, and HTML rendering.
- `ferrite-dev-server`: TSX-backed development server, route manifest rebuilds, static client asset serving, server-payload JSON/frame route responses, form-based server-action POST handling, explicit action references in the build manifest endpoint, and polling reload client.
- `ferrite-protocol`: render-packet/render-stream/client-reference/server-payload/server-payload-frame/server-action markers, versioning, packet shapes, and validation intended to become the native/WASM protocol boundary.
- `ferrite-protocol-wasm`: WASM build of Rust-owned server-payload packet and stream-frame validation for browser-capable JavaScript consumers.
- `ferrite-router`: app-directory route discovery, layout/loading/error convention discovery, and route type generation.
- `ferrite-ssr`: legacy serialized VNode decoding, versioned compact render-packet, render-stream, and server-payload decoding, plus server-side HTML rendering.
- `ferrite-node`: a minimal Node-API addon exposing the Rust SSR renderer to JavaScript consumers.
- `ferrite-cli`: human-first CLI for route inspection and project checks.

The Rust side should own work that benefits from predictable performance and strong validation: compiler passes, route manifests, SSR orchestration, generated types, dev-server routing, and build output.

## TypeScript Facade

- `@ferrite/protocol`: browser-safe TypeScript protocol package generated by Rust protocol codegen, exporting markers, versions, packet types, builders, and validators without depending on the DOM runtime or native Node bindings.
- `@ferrite/protocol-wasm`: TypeScript wrapper for the Rust `ferrite-protocol-wasm` artifact, exposing server-payload packet and stream-frame JSON validation through browser-capable WASM. Generated browser bundles can import its `.wasm` artifact and emit it under Ferrite's static asset path.
- `@ferrite/runtime`: JSX runtime, component types, `Suspense`, public hooks API, route-related types, and compatibility re-exports for the generated protocol APIs.
- `@ferrite/runtime/dom`: browser DOM mount/hydrate helpers, client-reference hydration, server-payload fetch/application helpers, incremental stream-frame application, same-origin payload navigation helpers with opt-in stream mode, managed head reconciliation, popstate restoration, payload prefetching, and idempotent server-action form enhancement/bootstrap.
- `@ferrite/runtime/server`: server helpers for rendering page modules, route loading/error conventions, and layout chains to legacy serialized VNodes, versioned render packets, versioned render-stream packets, or versioned server-payload packets, plus page/layout metadata collection, explicit `createServerAction()` form action references, and rendered-route server-action manifest collection.
- `@ferrite/node`: JavaScript package wrapper for the native Node addon, currently exposing `renderJsonToHtml(input: string): string`, resolving native bindings from an explicit override, local source build, or checksum-verified supported optional platform prebuild package, and validating generated prebuild package artifacts on the current host through the dedicated local Buildkite lane.
- `scripts/verify-npm-packages.mjs`: local release verifier for JS-facing npm package tarballs. It builds public packages, validates locally knowable package metadata, writes release-shaped manifests into temporary staging copies, runs real `npm pack --json` into temporary tarballs, validates packed file lists, inspects each packed `package/package.json`, rejects `private` and `workspace:*` in packed manifests, and rejects tarball paths or symlinks that resolve outside the fresh staging root. It computes a SHA-256 digest and exact byte size from every real tarball (including the current-host native prebuild), checks npm's reported size against the bytes, and writes a versioned report envelope binding the exact Git commit/tree, explicit local-or-Buildkite build identity, complete package-set digest, and retained tarball identities under `dist/npm-packages/`. It installs all generated tarballs together in a clean offline temp project with optional native dependencies omitted, smoke-imports the protocol/runtime/WASM-safe packages, checks the `@ferrite/node` tarball is installed without importing its unpublished optional native binding path, and leaves repository/homepage/bugs proof gated on a configured GitHub remote. `scripts/prepare-npm-release.mjs` reopens the retained archives and requires exact Buildkite/source identity; `scripts/publish-npm-release.mjs` revalidates and privately stages the same bytes immediately before each explicitly authorized publish. Source package manifests stay private and workspace-shaped for development.
- `packages/runtime/bin/render-page.mjs`: TSX page executor used by Rust dev/build orchestration; render/document modes emit versioned compact render packets, stream modes emit fallback shells plus resolved chunks, server-payload modes emit compact shells/chunks plus client-reference payloads, and server-action-manifest mode emits explicit form action references discovered during route render.
- `packages/runtime/bin/render-artifact.mjs`: production-only executor for verified self-contained server-module bytes supplied over stdin. It has no esbuild dependency and performs render, metadata, payload, stream, and route-registered action operations without source discovery or temporary compilation.
- `packages/runtime/bin/build-client.mjs`: browser bundle executor used by Rust dev/build orchestration; it uses TypeScript's emitted runtime module syntax and lexical binder to construct a deterministic compiler-owned runtime dependency graph for every page/layout tree, applies emitted-JavaScript extension substitution, erases type-only imports, includes static ESM, dynamic-import, CommonJS `require()`, and TypeScript `import = require()` edges, rejects source cycles, unresolved relative imports, and symlink escapes with actionable paths, records server-to-client boundaries as client references, skips route bundle emission unless the page or one of its layouts starts with `"use client"`, and can emit a standalone action-form bootstrap chunk for server-only action routes that have no client-reference script.
- `docs/deployment.md`: operator-facing deployment guide for the current production adapter, including proxy/TLS assumptions, build/start commands, smoke tests, observability, rollback, and known security gaps.
- `docs/observability.md`: experimental structured-event schema, correlation and privacy boundaries, backpressure behavior, compatibility notes, and explicit non-tracing limits.

The TypeScript facade exists for developer ergonomics. It should remain thin, typed, and compatible with normal TSX tooling. Browser DOM work and the current esbuild bridge live here because DOM and JS module graphs are JavaScript-native; Rust owns orchestration, routing, validation, SSR, static output, native SSR binding, protocol codegen, and CLI behavior.

## TypeScript Strategy

Ferrite should parse and transform TS/TSX in Rust, but semantic TypeScript compatibility should initially be delegated to the official TypeScript compiler. Reimplementing TypeScript's checker is out of scope until the rest of the framework is proven.

The CLI therefore treats TypeScript as an automatic project check:

1. Discover app routes.
2. Generate `.ferrite/types/routes.d.ts`.
3. Run local `tsc --noEmit --project tsconfig.json`.

## HTTP Input Boundary

The dev and production socket input boundaries share a deliberately narrow one-request HTTP/1.1 upstream contract. `httparse` 1.10.1 owns request-line and header syntax with its strict defaults; Ferrite layers exact CRLF framing, origin-form targets, a valid singular `Host`, no request `Transfer-Encoding` or `Expect`, and positive request bodies only for server-action POSTs with one decimal `Content-Length`. Framing and interpreted duplicate headers, malformed authorities, encoded separator/dot bytes in the path, request-target differentials, and already-buffered pipelined suffixes fail closed. Other repeated fields are comma-combined in wire order rather than silently using a last-value-wins map. A differential corpus records both malformed syntax rejected by `httparse` and general HTTP syntax that `httparse` accepts but Ferrite's upstream policy rejects. This shared boundary intentionally rejects direct HTTP/1.0, bare-LF, and absolute-form traffic in both modes so parser behavior does not diverge; browser HTTP/1.1 remains supported. Every response closes the connection. Production deployments should use the supplied authority-rejecting, buffering, and header-sanitizing nginx topology rather than exposing this application server as a general-purpose HTTP edge. For clean evidence, the candidate-image harness exports the exact Git commit into an immutable context and labels the image with its revision and tree. It then runs Ferrite with official nginx 1.29.3 selected by immutable multi-platform index digest on an isolated bridge network, records the resolved architecture and image identity, and exercises 43 raw HTTP/1 normal, failure, and odd paths, seven negotiated HTTP/2 edge paths, and fail-closed evidence controls. Nginx JSON access evidence also proves that five ambiguous-framing and nine malformed-target probes received no upstream status.

## Route Conventions

Ferrite scans for the nearest `loading.{tsx,ts,jsx,js}` and `error.{tsx,ts,jsx,js}` from the app root down to each page directory. Rust carries those paths in the route manifest and passes them to the TSX page executor during dev/build rendering.

- `loading.tsx` wraps streamed page output as a server `Suspense` fallback. Non-stream dev/build output still waits for the final page tree.
- `error.tsx` wraps the page tree with a server error boundary and renders `{ error }` when the page subtree fails. Layout failures outside that page boundary still surface as render errors.

The dev server renders matched HTML routes through the stream packet path and keeps both representations: a buffered HTML body for tests and `--once`, plus shell/chunk parts for real HTTP sockets. The socket writer emits `Transfer-Encoding: chunked` only when stream chunks exist; routes without deferred chunks keep `Content-Length`. Matched app routes can also negotiate the raw validated server-payload protocol JSON with `?__ferrite_payload=server` or line-delimited shell/chunk frames with `?__ferrite_payload=stream`; unsupported reserved payload values return `400 Bad Request`.

The production HTTP adapter uses the same input parser and stream response model without dev reload state, but its artifact execution boundary is different from development. `ferrite build` stages a complete candidate directory, validates a digest-bearing client-compiler input snapshot, rechecks static-parameter and action-bootstrap preflight state, compiles one self-contained server module and parameter-independent browser bundle per route, and rejects source drift before writing the versioned `ferrite-server.json` manifest. It then replaces the destination with rollback on activation failure. The direct directory replacement is staged, not an atomic release-pointer swap. `ferrite serve` validates the format/build identity, normalized relative paths, route uniqueness, declared public URLs, file sizes, SHA-256 digests, and symlink containment before startup. It retains verified module and asset bytes in immutable route state and invokes `render-artifact.mjs` with module bytes over stdin, so replacing or deleting the source artifact after startup cannot create a mixed-build process. It never scans `app/`, writes route types, imports esbuild, rediscovers action manifests, or runs the client bundler. Dynamic routes without prerenders remain renderable from their prebuilt modules. Production sockets run through a bounded worker pool with absolute request-read and whole-response-write deadlines, immutable route state is shared through `Arc<ProductionProject>`, and replay nonces alone use a narrow mutex, so independent route work is not globally serialized. The CLI maps `SIGINT` and `SIGTERM` to the shutdown-aware listener, which stops admission and joins accepted work; the container template uses `exec` so those signals reach Ferrite. The adapter otherwise preserves payload JSON/frame modes, same-origin route-registered form actions, CSRF/replay/proxy controls, compression, immutable asset caching, route-pattern metadata, request/action observers, stderr logs, metrics, and graceful drain behavior.

Server actions are currently form-based and explicit. A server-rendered `<form action={createServerAction({ id, run })}>` becomes a same-origin `POST /_ferrite/action` with hidden `__ferrite_action` and `__ferrite_route` fields, plus hidden `__ferrite_csrf` when the Rust renderer is configured with a server-action CSRF token and hidden `__ferrite_nonce` when production replay nonce enforcement is enabled. Rust requires a valid `Host` header for action POSTs, rejects a present `Origin` or `Referer` host that differs from the request `Host` by default, switches to a configured trusted proxy public origin when `--trusted-proxy-public-origin` or `ProductionTrustedProxyConfig` is set, rejects missing or mismatched `X-Forwarded-Proto`/`X-Forwarded-Host` in that trusted-proxy mode, only trusts `X-Forwarded-For` for logged `client_ip` when `--trusted-proxy-client-ip-hops` is configured, rejects missing or mismatched `__ferrite_csrf` values when a token is configured, can additionally require a matching cookie named by `--server-action-csrf-cookie-name`, and can consume one-time in-process replay nonces when `--server-action-replay-ttl-ms` is enabled. The CSRF cookie is emitted on production route responses with `Path=/; SameSite=Lax; HttpOnly; Secure`. The adapter then parses urlencoded forms and small text multipart forms, rejects file parts, validates the server-action request shape through `ferrite-protocol`, matches the submitted route path against the immutable artifact route registry, invokes its prebuilt module, and accepts only an action registered while rendering that route with the submitted request parameters. Action ids observed during build are diagnostic metadata rather than a complete pre-execution allow-list, which avoids false rejection of parameter-conditional actions. The adapter emits action audit events for accepted and rejected attempts and returns validated `server-action-response` JSON. `@ferrite/runtime/dom` exposes `enhanceServerActionForms()` for explicit integration and `bootstrapServerActionForms()` for generated browser entrypoints; route client bundles, client-reference chunks, and standalone server-only action bootstrap chunks call the bootstrap helper on `document` and the helper deduplicates per event root. Build output and the dev build manifest endpoint include explicit `server_action_manifests` entries collected from rendered `createServerAction()` form references, and the client bundle manifest can include an `actionBootstrap` script while keeping route-level `script: null`. A Chromium-backed test builds a temporary Ferrite app and proves enhanced form submissions stay on-page and send `FormData` for route, island, and server-only action assets. This does not yet include automatic `"use server"` export discovery, deployment-stable inferred action ids, persistent deployment registries, session-bound token rotation, distributed replay nonce storage, cross-origin action calls, upload streaming, client event actions, or external action audit sinks.

The production in-flight limit counts both queued and active sockets and rejects excess connections with `503`. Worker-pool admission clears nonblocking mode inherited from the listener before any request read; otherwise a read racing ahead of the first request bytes can surface `WouldBlock` as a false `408`. The request reader recalculates the remaining absolute budget before every header/body read, so trickled bytes cannot renew the timeout; timeout responses shut down unread input before writing so pending bytes do not reset the `408`. Rejected sockets apply the same input shutdown before the bounded response and close the write side afterward. The configured subprocess deadline kills an artifact-runner process and returns generic `504` HTML; non-timeout production failures return generic `500` HTML while detailed diagnostics go to stderr. The response writer recalculates the remaining absolute budget before each header, fixed-body, gzip, and chunked write and applies that remaining time to the socket operation. Stalled-reader and trickled-writer socket tests prove both deadline directions. Local artifact-backed tests prove overlapping slow requests, bounded `503` saturation and recovery, concurrent slow-reader handling, bounded sustained mixed-load resource behavior, clean `SIGTERM` drain, and reuse after a failed runner subprocess. Long-duration hosted capacity, host-process supervisor recovery, multi-process replay storage, and hosted horizontal scaling remain unproven.

Expected public server-action failures must use `FerriteActionError` with a validated stable code and nonempty message. Unexpected exceptions terminate the renderer and become generic production `500` responses while their details remain on stderr. Version-1 error packets without a code remain readable for backward compatibility. The optional single-process replay store allocates only after a route match, holds at most 4,096 live nonces, and evicts the oldest unused nonce under capacity pressure; session binding and distributed replay coordination remain outside the current claim.

## Client Hydration Boundaries

Routes are server-first. The browser bundler inspects the matched page and layout chain for a leading `"use client"` directive before doing any esbuild work. If no directive is present, the route returns a server-only bundle record with `script: null`, empty asset lists, and no generated route files. Client and client-reference bundles use esbuild file loaders for imported binary/static assets, including `.wasm`, and pass Ferrite's configured static public path into esbuild so generated browser code references emitted assets through `/_ferrite/static/...` rather than temp-directory-relative URLs. Production builds remove the static client output directory before rebuilding so a route that becomes server-only cannot keep stale scripts from an earlier build.

Every route and layout chain produces a deterministic `moduleGraph` in the client bundle manifest. The graph uses TypeScript's emitted runtime module syntax plus its lexical binder rather than source regexes, honors the project's parsed `tsconfig.json` `verbatimModuleSyntax` setting, contains normalized project-relative `.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.cts`, `.mjs`, and `.cjs` files with byte-sorted runtime edges, and covers static ESM imports/exports, static-literal dynamic imports including imports with an options argument, unshadowed static CommonJS `require()` calls, TypeScript `import = require()` declarations, and client-module dependencies. Explicit type-only syntax and imports used only in erased type positions are omitted when the project compiler semantics erase them. Extensionless specifiers resolve only `.tsx`, `.ts`, `.jsx`, `.js`, and their index variants, matching the default esbuild and server-bundler contract; `.mts`, `.cts`, `.mjs`, and `.cjs` dependencies require an explicit extension. Explicit `.js`, `.jsx`, `.mjs`, and `.cjs` specifiers fall back to their TypeScript source counterparts only when the same-named runtime file is absent. Every missing higher-priority candidate, selected symlink path, missing root `tsconfig.json`, and local, inherited, external, or symlinked TypeScript config read is recorded in the digest-bearing input snapshot, so creating a runtime file that outranks a prior source fallback or changing compiler semantics invalidates the development route. Resolved source paths are canonicalized before graph recording; a cycle is rejected with the complete path, malformed or unresolved TypeScript configuration fails clearly, an unresolved relative source import identifies its importer, and parent, cross-drive, UNC, or symlinked runtime dependencies that escape the project root fail closed. Rust validates portable graph paths, canonical byte ordering, edge targets, acyclicity, nonempty-graph client-reference membership, absolute snapshot paths, snapshot entry ordering, kinds, and current values before accepting the compiler result.

When a server module imports a module with a leading `"use client"` directive through concrete default or named ESM bindings, the scanner records that server-to-client boundary in `clientReferences` with a stable `module`, `exportName`, and `id` of `module#exportName`, then still traverses its relative dependencies for graph correctness. Namespace, side-effect, CommonJS `require`, TypeScript import-equals, dynamic-import, and star-re-export boundary forms are rejected before browser output because they do not identify a concrete component export; those forms remain valid graph edges when they do not cross a `"use client"` boundary. Nested client-to-client imports remain graph edges rather than extra server-reference boundaries. Each supported reference records its own `script`, `styles`, `outputs`, `sourcemaps`, and `assets`; the parent route bundle aggregates those outputs while keeping route-level `script: null`.

The scanner hashes the exact source and TypeScript configuration bytes it consumed and records each resolver candidate's selected, missing, outside-project, or error state. After bundling, Node verifies that snapshot and retries the complete graph-plus-bundle operation once if any input changed; two consecutive mixed-state attempts fail. Rust then independently recomputes the declared snapshot before accepting the bundle. Development retains that same snapshot per route and recomputes it during reload polling. A content change, deletion, restoration, new higher-priority resolver winner, layout dependency change, or local/external/symlinked TypeScript configuration change advances the development build id even when the dependency is outside `app/`; removing a route drops its old watch set. Production build rechecks static/action preflight state after bundle acceptance and validates the snapshot again after server-module and prerender work, so source drift fails the staged build instead of activating mixed client/server output. Installed production artifacts remain immutable and do not poll source files.

The runtime island contract is explicit, but app code no longer writes the marker by hand for imported client components. During server page bundling, nested modules with a leading `"use client"` directive are replaced with server-side client-reference proxies. A proxy renders a `<span>` island container with `data-ferrite-client-reference="module#exportName"`, legacy JSON `data-ferrite-client-props`, a versioned `data-ferrite-client-payload` containing `{ ferrite, version, id, module, exportName, props }`, and fallback HTML from the original client component. The emitted client-reference chunk registers the real browser component and calls `hydrateClientReference()`, which validates the payload, hydrates matching containers, and marks them with `data-ferrite-client-hydrated="true"`. Rust validates the JS-produced manifest entries before build/dev adapters consume them.

The `server-payload` protocol packet is the first RSC-style transport layer. It carries a compact shell, shell-level `clientReferences`, deferred stream chunks, and per-chunk `clientReferences`. The Rust protocol crate owns validation, the generated `@ferrite/protocol` package exposes `validateServerPayloadPacket()`, `@ferrite/protocol-wasm` exposes Rust-backed `validateServerPayload()` for full packets, `@ferrite/runtime/server` emits payloads from the same rendered tree used for HTML, `ferrite-page-renderer` can request page/document payloads through `--server-payload` and `--document-server-payload`, and dev/production adapters can return those validated packets directly over HTTP. The protocol crate also owns a line-delimited `server-payload-frame` contract for incremental payload application: one validated shell frame followed by zero or more validated chunk frames. Dev and production adapters expose that framed contract over HTTP with `?__ferrite_payload=stream`; `@ferrite/protocol-wasm` also exposes Rust-backed `validateServerPayloadStreamFrameJson()` and typed `validateServerPayloadStreamFrame()` helpers for those frames.

The DOM runtime can fetch a server-payload response for a route, validate it, merge returned chunk roots into matching `data-ferrite-suspense-boundary` shell markers, convert compact nodes back into Ferrite children, and apply the result through the existing mounted-root update path. It can also consume a readable stream of line-delimited server-payload frames, commit a validated shell before deferred chunks arrive, then apply later validated chunk frames through the same compact-node/chunk path. The navigator helper wraps a mounted root, exposes an explicit same-origin prefetch API, optionally prefetches safe links on pointer/focus intent, consumes prefetched packets once during navigation, intercepts safe same-origin link clicks, applies payload responses, can opt navigation and popstate restoration into `?__ferrite_payload=stream` with JSON fallback before shell commit, updates history with `pushState`/`replaceState`, stores payload URLs in framework-marked history state, restores marked back/forward entries through the same payload path, extracts the route root from document-shaped payloads when possible, reconciles framework-managed title/meta/link/script/style head nodes while preserving unrelated head nodes, and falls back to normal navigation after failed intercepted or restored payload requests. A Chromium-backed integration test now proves same-origin prefetch consumption, URL/title updates, stream shell fallback rendering, later chunk application, stream-mode back/forward popstate restoration, malformed programmatic payload rejection without DOM/history mutation, and malformed clicked-payload fallback to normal document navigation against real browser fetch, stream bodies, and history APIs.

This is a working imported-client island boundary with a first server payload stream and first form-based server-action transport. It proves the Rust orchestration can distinguish server modules, whole-route client modules, imported client references, and explicit route-scoped action references through static output, manifests, emitted browser artifacts, automatic server markers, runtime hydration, HTTP payload responses, browser payload application/navigation helpers, incremental browser stream-frame consumption, HTTP frame-stream negotiation, navigator stream-mode selection, form POST action invocation, explicit action manifest emission, idempotent generated browser action-form bootstrap for route, client-reference, and server-only action assets, Chromium-backed action form enhancement proof, Chromium-backed payload prefetch/navigation, stream-frame, popstate, malformed-payload rejection, and malformed clicked-payload fallback proof, gzip response compression, managed head reconciliation, popstate restoration, payload prefetching, immutable production asset fingerprints, preload hints, bounded production request handling, production render timeouts, request observer hooks, production action audit logs, trusted-proxy public-origin checks for action POSTs, explicit trusted forwarded client-IP log policy, graceful production shutdown, reusable production workers, first-pass systemd/nginx/container deployment templates, an operator-facing deployment guide, validated payload/action packets, a generated browser-safe protocol package, a Rust-backed WASM protocol validation package for full server-payload packets and stream frames, generated browser-bundle emission for protocol WASM assets, native Node binding resolution that can use source builds or checksum-verified optional platform prebuild packages, current-host native prebuild verification in the dedicated local Buildkite lane, and a local npm package verifier that inspects and clean-installs JS-facing staged tarballs without registry credentials. It is not yet Flight-compatible React Server Components, and production distribution still lacks npm-published WASM/native packages, exact-platform Linux/Windows/Intel-macOS proof, hosted staging proof for the deployment templates, code-signing/notarization, external metrics/tracing/audit sinks, and automated npm release publishing.
